# wtcompose

[日本語](./README.md)

A CLI that generates a `docker-compose.override.yml` assigning each git worktree
its own unique `container_name` and host ports, so multiple worktrees of the
same repository can run the same `docker-compose.yml` concurrently.

When you develop on several worktrees of the same repository in parallel,
`docker compose up` fails for one of them the moment `container_name` or a
host port collides. wtcompose solves this by automatically assigning a
unique value per worktree.

## Features

- **Automatic port assignment**: generates a unique `container_name` and host ports for each worktree, without touching `docker-compose.yml` itself
- **Persistent assignments**: assigned ports are saved to `~/.config/compose-worktree-override/ports.tsv`. The same repo/worktree/service/original-port combination reuses the same value on later runs
- **Transparent docker compose wrapper**: subcommands like `wtcompose up` / `wtcompose down` / `wtcompose ps` run exactly like their `docker compose` equivalents, with the override regenerated first
- **herdr integration**: shows, in the [herdr](https://herdr.dev) sidebar, which ports the containers actually running in the current directory are listening on right now
- **Shell completion**: bash/zsh/fish completion that delegates to docker compose's own
- Single binary, no `yq` dependency

## Requirements

- Git
- Docker Compose 2.24+ (needs support for the `ports: !override` tag)
- macOS or Linux (docker compose subcommands are run via process replacement (`exec`), so Windows isn't supported)

## Usage

Run it in a directory that has a `docker-compose.yml`.

```sh
cd path/to/worktree
wtcompose
```

- Generates `docker-compose.override.yml` for every service that declares `container_name` or `ports`
- `container_name` becomes `<repo>-<worktree>-<service>` (or just `<repo>-<service>` when repo and worktree names match, i.e. the main worktree)
- Each `ports` host side is assigned a free port (starting at 20000) persisted in `~/.config/compose-worktree-override/ports.tsv`
- The original `docker-compose.yml` is never modified
- The generated `docker-compose.override.yml` is registered in `.git/info/exclude`, so it never shows up in `git status`
- If no service needs an override, nothing is written, and any override this tool previously generated is removed
- Refuses to overwrite an existing `docker-compose.override.yml` it didn't generate itself

Appending any `docker compose` subcommand to `wtcompose` regenerates the override and then runs `docker compose <args>`:

```sh
wtcompose up -d
wtcompose ps
wtcompose logs -f web
wtcompose down
```

- Stdio, signals, and the exit code are identical to calling `docker compose` directly
- Override-generation messages go to stderr, so piping stdout (e.g. `wtcompose ps --format json | jq`) works exactly as it would with plain `docker compose`
- `herdr` is reserved as wtcompose's own subcommand, so it's never forwarded to `docker compose herdr` (see [herdr integration](#herdr-integration))
- If `-f`/`--file` or `COMPOSE_FILE` names an explicit compose file, `docker-compose.override.yml` won't be auto-loaded and port isolation stops working, so wtcompose refuses with an error. Run `docker compose -f ...` directly in that case
- If generating the override fails (e.g. an existing `docker-compose.override.yml` this tool didn't generate), no subcommand runs, including `down`/`ps`. Call `docker compose down` directly to work around it

### Example

`docker-compose.yml`:

```yaml
services:
  web:
    image: nginx:alpine
    container_name: myapp-web
    ports:
      - "8080:80"
      - "8443:443"
  db:
    image: postgres
    container_name: myapp-db
    ports:
      - "5432:5432"
```

Running it in the main worktree (`myapp/`):

```
$ wtcompose
✅ docker-compose.override.yml を生成しました(myapp/myapp)
# generated by compose-worktree-override
services:
  web:
    container_name: myapp-web
    ports: !override
      - "20000:80"
      - "20001:443"
  db:
    container_name: myapp-db
    ports: !override
      - "20002:5432"
```

Running it in another worktree (`myapp-feature/`) assigns a different container_name and host ports for the same repo:

```
$ wtcompose
✅ docker-compose.override.yml を生成しました(myapp/myapp-feature)
# generated by compose-worktree-override
services:
  web:
    container_name: myapp-myapp-feature-web
    ports: !override
      - "20003:80"
      - "20004:443"
  db:
    container_name: myapp-myapp-feature-db
    ports: !override
      - "20005:5432"
```

## Shell completion

Every `wtcompose` subcommand except `herdr` maps directly onto `docker compose` arguments, so completion is delegated wholesale to docker itself. Everything `docker compose` knows how to complete - subcommands, flags, service names, even running container names - works out of the box.

```sh
# bash (add to ~/.bashrc)
source <(wtcompose completion bash)

# zsh (add to ~/.zshrc; compinit must already have run)
source <(wtcompose completion zsh)

# fish
wtcompose completion fish | source
```

Requires `docker` to be installed.

## herdr integration

[herdr](https://herdr.dev) is a terminal multiplexer for coding agents. Since the ports assigned per worktree change every time you switch worktrees, `wtcompose herdr` keeps the herdr sidebar showing which ports the containers **actually running** in the current directory are listening on right now.

### Setup

1. Add a token row to `[ui.sidebar.spaces]` in `~/.config/herdr/config.toml` (append to any existing rows):

   ```toml
   [ui.sidebar.spaces]
   rows = [["state_icon", "workspace"], ["branch", "git_status"], ["$wtcompose_ports"]]
   ```

   Takes effect after `herdr server reload-config`. The row simply doesn't render for a workspace that hasn't reported a token.

2. Inside a pane herdr manages (`$HERDR_WORKSPACE_ID` must be set), `wtcompose up` automatically starts the watcher in the background, and `wtcompose down` automatically stops it and clears the token:

   ```sh
   wtcompose up -d   # 👀 herdr ウォッチャーをバックグラウンドで起動しました(pid=...)
   wtcompose down    # clears the token and stops the watcher
   ```

   Running `wtcompose up` more than once for the same workspace only ever starts one watcher (pid file at `~/.config/compose-worktree-override/herdr-watchers/<workspace_id>.pid`, log alongside it as `.log`). If you bypass wtcompose and call `docker compose up` directly, start the watcher yourself:

   ```sh
   wtcompose herdr
   ```

   It polls `docker compose ps --format json` every 5 seconds by default and keeps reporting a string like `web:20000 db:20002` as the `wtcompose_ports` token. Change the interval with `--interval` (e.g. `wtcompose herdr --interval 10s`).

   `Ctrl-C` clears the token before exiting. If the process is killed outright, the token's TTL (3x the polling interval) expires it from the sidebar automatically.

## Supported port formats

For `ports` entries where the host side is a single explicit port number, wtcompose reassigns it to a worktree-unique value:

- short syntax: `"host:container"` (including `"host:container/tcp"` / `/udp`)
- long syntax: mapping entries whose `published` is a single port number (`target:`/`published:`/`protocol:` etc; every other field is preserved as written)

The following are passed through unchanged (their host-port collisions aren't resolved):

- bind-address-prefixed (`"127.0.0.1:8080:80"`)
- port ranges (`"8000-8010:8000-8010"`, or long syntax with `published: "8000-8010"`)
- container-only (`"80"`, or long syntax with `published` omitted)

Free-port selection only avoids ports already recorded in `ports.tsv`; it never checks whether a port is actually bindable on the host.
